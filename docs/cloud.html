Cloud

Strata Cloud

The hosted version. We run the infrastructure, you sign in with GitHub, and a repository you already have access to becomes your data modelling workspace. There is nothing to install and no server to keep alive.

Getting started

  1. Sign in with GitHub

    Open strata-demo.onrender.com and choose Continue with GitHub. There is no separate account to create, no password to pick and no email to confirm.

    GitHub will ask you to authorise Strata. It asks for repository access because that is where your models live and where pull requests get raised.

  2. Choose a repository

    You are shown the repositories you can write to. Pick the one holding your models, or an empty one if you are starting fresh.

    Only repositories you can write to are offered. A repository you can only read cannot receive a model change, so opening it would give you a workspace where every save fails at the last step.

  3. Work

    The first time a repository is opened it is cloned, which takes a moment. After that it is already there. Draw a diagram, edit a table, and propose the change as a pull request in your own repository.

Free while in preview

Cloud runs on a free tier today, which has two visible effects: it sleeps after fifteen minutes of no traffic, so the first request after a quiet spell takes about a minute, and its disk is wiped on restart, which signs everyone out and re-clones. Neither loses work, because your models are in your repository. There is no uptime commitment yet.

Your repository is the workspace

This is the decision everything else on this page follows from, so it is worth stating plainly: a workspace is a GitHub repository. Not a project we keep for you that happens to sync somewhere.

Three things fall out of that, and they are the reason it is built this way.

Onboarding is repository access. You add a colleague to the repository in GitHub and they can sign in and work in the same models. There is no invitation to send, no seat to assign, and no second list of people that slowly stops matching the first.

Two people who open the same repository get the same workspace. Not a copy each. They are editing the same files, and Strata shows who else is in there.

Leaving is not a migration. Your models are already in your repository, in plain YAML, in a format the command line tool reads without any of this. Stopping means closing the tab.

Who can see your models

Exactly the people who can already see the repository. Strata asks GitHub every time a workspace is opened rather than keeping its own copy of who is allowed in, so access removed in GitHub is access removed here, with nothing to synchronise and nothing to remember to revoke twice.

Your permission on the repository becomes your role:

On the repository In Strata What that allows
Admin Admin Everything, including settings and user administration
Write Editor Edit models, propose pull requests
Read Viewer Read models and diagrams, change nothing
Changes to permissions take effect at the next sign-in

Your role is worked out when you open a workspace and held for the session, because asking GitHub on every request would spend an account's whole hourly API allowance on page loads. Sessions last twelve hours. If you need a permission change to apply immediately, sign out and back in.

What we store

A working copy of your repository, so the editor has something to read, and a note of which repository your session is pointed at. That is the whole list.

The working copy is disposable. It can be deleted at any time and is rebuilt by cloning your repository again. Your repository remains the record of what your models actually are, which means an outage here is an inconvenience rather than a loss.

Your GitHub access token is held in your session cookie, encrypted rather than signed. A signed cookie is readable by anyone holding it, and what they would be reading is a live credential for your source control.

GitHub Enterprise

Enterprise Cloud works with no changes. It is github.com with single sign-on in front, so signing in behaves the same way. Your organisation may require you to authorise the token for single sign-on the first time, which is one extra click on GitHub's side.

Enterprise Server is a different host, so it needs an instance pointed at it. That is a self-hosted deployment with two extra settings, covered in configuration. Your Enterprise Server is usually inside your own network, which a hosted instance cannot reach anyway.

Cloud or self-hosted

The same software either way. The question is only who runs it and where the working copy sits, since in both cases your models live in your own git repository.

Cloud Self-hosted
Who runs the server We do You do
Where your models live Your GitHub repository Your GitHub repository
Where the working copy lives Our infrastructure Yours
Sign-in GitHub Local accounts
Private network access No Yes
Setup None About fifteen minutes

Choose self-hosting if your repository is on an internal GitHub Enterprise Server, if your BigQuery project is only reachable from inside your network, or if a review says the working copy cannot leave your infrastructure. Those are the cases Cloud genuinely cannot serve, and the container is the same one we run.

Note that deploying the container to Render, Fly or Google Cloud Run is self-hosting, not Cloud: you own the instance and the data either way. Those options are compared in hosting options.
