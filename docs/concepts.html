Concepts

How the model works

Enough to be useful, not a full reference. If you have used a modelling tool before, most of this will be familiar. The parts that are different are called out.

The three tiers

Not three views of one thing. Three separate models, linked by derivedFrom, so you can change the physical layer without touching the business definitions above it. 

conceptual  ──▶  logical  ──▶  physical
   │               │              │
 Customer      Customer       dim_customer
 Order         Order          fct_order

 ideas and     attributes,    STRING, NUMERIC,
 how they      keys, logical  partitioning,
 relate        types          clustering
TierHoldsAnswers
Conceptual Concepts, relationships, glossary terms, subject areas What does the business talk about, in its own words?
Logical Entities, attributes, keys, logical types What are the things, and what identifies them?
Physical Tables, columns, BigQuery types, partitioning, clustering What will actually exist in the warehouse?

The physical tier can have several layers inside it, usually raw, staging and mart. Mappings between layers carry the transformations: slowly changing dimension strategies, surrogate keys, point in time lookups, conformed dimension registration.

You do not have to use all three

Plenty of teams start with just a physical model and add the layers above it later, or never. The chain is there when you want it and does not get in the way when you do not.

What a file looks like

Every object is YAML. Here is a table:

models/shop_warehouse/tables/dim_customer.yaml

id: tbl_dim_customer
kind: table
name: dim_customer
model: shop_warehouse
objectType: table
description: One row per customer.
layer: mart
grain: One row per customer.
columns:
  - id: col_dc_customer_id
    name: customer_id
    dataType: STRING
    mode: REQUIRED
  - id: col_dc_email
    name: email_address
    dataType: STRING
    mode: NULLABLE
    classification:
      sensitivity: confidential
      categories:
        - pii
primaryKey:
  - customer_id
clusterBy:
  - customer_id
entityRef: shop_logical:Customer

Three fields do the important work:

  • id is stable and never changes, so renaming a table does not break anything that points at it.
  • kind is what the object is. The loader reads this, not the folder name.
  • model is which model owns it.

That is the whole trick. Because every file says what it is and where it belongs, nothing has to be inferred from where it sits.

Why the layout does not matter

Most tools care deeply about your folder structure. Strata does not, and that is a deliberate design choice with a practical payoff: you can reorganise whenever your team's thinking changes. 

strata reorganize --preset by-layer --dry-run

Every file moves. Nothing about the model changes. A test in the repository asserts that switching between any two layouts leaves the semantic content byte for byte identical.

So if your team starts out organising by model and later decides warehouse layer is the more useful grouping, that is one command, not a migration.

Domains and classification

A domain is a reusable definition of a kind of value. Define email_address once, say it is personal data, and every column that uses it inherits that.

domains/email_address.yaml

id: dom_email_address
kind: domain
name: email_address
description: An email address.
logicalType: string
physicalType: STRING
nullable: true
classification:
  sensitivity: confidential
  categories:
    - pii

Classification flows down a chain, and each step can override the one before it:

column  ◀──  its domain  ◀──  logical attribute  ◀──  that attribute's domain

Merged field by field, not all or nothing. So a column can take the sensitivity from its domain while setting its own categories.

From classification, Strata generates BigQuery policy tags, using a map you define in strata.config.yaml. That is how a business statement like "email addresses are personal data" becomes an actual access control in the warehouse.

Skills

Skills are rules your team writes for itself, and they run automatically when somebody proposes a change. A blocking skill refuses the proposal.

They live in your repository at .strata/skills/*.md, for the same reason the model does: a rule that governs what may merge is a decision worth reviewing, versioning and blaming.

Two kinds:

KindWhat it isNeeds
check Deterministic, instant and free. Parameterises one of the built in rules, such as "every table must have a grain" or "these words are forbidden in a name". Nothing.
agent A prompt run over the model by a language model, for judgements a rule cannot express. "Does this table's grain match its name?" A model provider key that you supply.

Without a key, an agent skill reports itself as skipped rather than passing. A governance control that quietly does nothing is worse than one that is visibly off.

Do not make an agent skill your only gate

Model content arrives by pull request, and a table description can attempt to steer the verdict. Agent skills only report and have no write path, which keeps the damage small, but treat them as advice rather than enforcement. Deterministic check skills and strata check in CI are what actually hold a line.

The workflow

What actually happens when somebody changes a model.

  1. They edit

    On the diagram, in the properties panel, in the data dictionary grid, or in the YAML dialog. Every change writes a file.

  2. Changes accumulate

    The Changes page shows what has changed, the same set git status would show. Nothing has been committed yet.

  3. They press Propose

    Strata validates the model, runs the skills gate, then creates a branch, commits, pushes, and opens a pull request.

    If validation fails, the proposal is refused. There is an override, because sometimes you genuinely need to share work in progress, and it is recorded.

  4. Somebody reviews it

    In GitHub, like any other pull request. CODEOWNERS decides who has to approve. The strata check job decides whether it can merge.

  5. It merges

    Strata notices, and fires whatever integrations you have configured: update the Confluence page, comment on the Jira ticket, post to the channel.

Notice what is not in that list. There is no separate approval system, no second history to reconcile, and no state that only exists inside strata. Every step uses something your team already has.
