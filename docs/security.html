Security

What is protected, and by whom

The most useful thing a self-hosted tool can give a security reviewer is a plain statement of which side of the line each thing sits on. Without it, every review invents its own answer and then asks you to confirm it.

Who protects what

Strata is responsible forYou are responsible for
Checking authentication and role on every route Terminating TLS
Encrypting stored credentials, and never returning them to a browser Who can reach the port, and your firewall
Refusing to read or write outside the workspace directory Backing up the data volume
Escaping generated output, so model content cannot become script The scope of the GitHub token you give it
Never executing model content The permissions on any service account
Refusing outbound requests to private and link-local addresses Branch protection on your model repository
Keeping one tenant's workspace and credentials away from another Keeping the image up to date
The one people miss

Branch protection. Strata generates CODEOWNERS and can refuse to open a proposal, but nothing stops somebody pushing straight to main if the repository does not require review. The governance story is only as strong as the repository settings underneath it.

Neither side is responsible for whether a model somebody approved is correct. Strata validates structure. It does not validate business meaning. Worth saying, because a governance tool invites the assumption that it does both.

Before you go public

Run through this before Strata is reachable from any network you do not control. It takes about ten minutes.

  1. Seed the administrator

    Set STRATA_ADMIN_USERNAME and STRATA_ADMIN_PASSWORD_HASH. Without them, first run setup is open, and it reopens every time the data directory is empty.

    How to check: restart the service and try to load the setup page. You should be sent to sign in instead.

  2. Make the data directory persistent

    A volume, not an emptyDir and not a container filesystem. Losing it signs everyone out, loses stored credentials and the audit log, and reopens setup unless the admin is seeded.

    How to check: restart the service and sign in again. If you have to create an account, the volume is not mounted where you think.

  3. Turn on Secure cookies and proxy trust

    STRATA_COOKIE_SECURE=true once you are on HTTPS, and STRATA_TRUST_PROXY=true if anything sits in front.

    Without proxy trust, the sign in throttle counts every visitor against one address, so one attacker can lock out your whole company.

  4. Decide what the deployment permits at all

    If anonymous people can reach it, set STRATA_FEATURES="". Otherwise every visitor can configure an integration, which means making your server send a request to a URL of their choosing.

    How to check: call /api/integrations. It should return 404.

  5. Check the headers survived your proxy

    curl -sI https://your-host/api/health

    You want content-security-policy, x-content-type-options, x-frame-options and referrer-policy. If any are missing, something in front of Strata is stripping them.

  6. Turn on branch protection

    In your model repository, require a review and require the strata check job to pass. This is the step that makes every other governance feature real.

  7. Give the GitHub token the smallest scope that works

    repo on the model repository. Nothing else. A fine grained token scoped to one repository is better than a classic token that can reach everything you can.

  8. Decide about single sign on

    Strata has none yet. Local passwords with no second factor on an internet-facing instance is a weak posture. Either put an authenticating proxy in front, or accept the risk knowingly and keep the instance on a private network.

What Strata does for you

Stated so a reviewer does not have to work it out from the source.

Access control

  • Three ordered roles, checked on the server for every request. The UI hides what your role cannot do, but the server is the thing that enforces it.
  • Passwords are hashed with scrypt. An unknown username takes the same time to reject as a wrong password, so the two cannot be told apart.
  • Sign in has per address and per account backoff, so guessing is not free.
  • Sessions are signed tokens with a twelve hour expiry. The role is read fresh from disk on every request, so demoting somebody takes effect on their next click.
  • The last administrator cannot be removed, so you cannot lock yourself out.

Handling files

  • Every path is resolved against the workspace root and checked, including the case where a sibling directory shares a prefix with it. That is the version most implementations get wrong.
  • Null bytes in paths are rejected.
  • git is run with an argument array and no shell, so there is no command injection.

Credentials

  • Encrypted with AES-GCM, stored outside the model repository, never sent to a browser.
  • The UI shows the last four characters so you can tell which credential is in place.
  • A mounted file is supported and preferred, so the value never has to touch Strata's own disk.
  • Log lines redact any value under a key that looks like a secret.

Outbound requests

  • Hostnames are resolved and checked against loopback, link-local, private and carrier grade NAT ranges before the connection is made.
  • Every address a name resolves to is checked, not just the first, so a name that resolves to one public and one private address is refused.
  • Redirects are followed by hand and each hop is re-checked.
  • The same check applies to git remotes, so a push cannot reach an internal address either.

Output

  • Generated HTML escapes cell content. Column descriptions are attacker controlled, and this is what stops a stored script reaching a published wiki page.
  • A content security policy is sent on every response, so a missed escape is a nuisance rather than an incident.

Supply chain

  • The server has two runtime dependencies. Almost everything in the lockfile is build and test tooling that never reaches the image.
  • The container runs as a non-root user with a pinned uid, all capabilities dropped, and no privilege escalation.
  • CI pins every GitHub Action to a commit hash rather than a tag, because a tag can be moved.

Known limits

Said plainly, because a security page that only lists strengths is not useful.

LimitWhat to do about it
No single sign on. Local accounts, no second factor. Put an authenticating proxy in front, or keep the instance on a private network.
No fine grained permissions. An editor can edit every model, not just their own. Use separate instances per team if that matters, or rely on branch protection for what actually lands.
Agent skills read model content that arrives by pull request. A table description can try to steer the verdict. The blast radius is limited on purpose: agent skills only report, and have no write path. Treat that as a rule, not an accident. Do not rely on an agent skill as your only gate.
A large model repository can be slow to load. Strata parses what is in the repository. Normal for a repository you control. Worth knowing if you let untrusted people open pull requests against it.
An administrator with shell access can edit the audit log. Ship the structured logs to your own pipeline if you need tamper resistance. Strata writes them to stdout in a form a collector can index.
One replica only. Not a security limit, but worth knowing: there is no high availability story today.

The audit log

Model changes are already auditable, because they are commits. Instance changes were not, and that was the gap: an administrator could disable a blocking governance rule and leave no trace anywhere, so the next pull request merged without a control everybody believed was running.

The audit log records who did the privileged things:

  • Signing in, and failing to sign in
  • Creating the first administrator
  • Creating, changing, disabling or removing an account
  • Setting or clearing a credential
  • Saving, testing or deleting an integration
  • Enabling or disabling a governance skill
  • Changing settings, file layout, or the git remote

Administrators read it in the UI, or from /api/audit. It is append only, one JSON object per line, in the data directory. Passwords never appear in it.

It is not tamper proof, and pretending otherwise would be theatre. It answers "what changed and who changed it" for an honest operator and for an incident review. If you need more than that, collect the structured logs off the machine.

Reporting a problem

Please do not open a public issue. A public issue tells everyone running Strata about the problem at the same moment it tells us.

Use GitHub's private vulnerability reporting, on the Security tab of the repository, or the address in the repository’s SECURITY.md.

Things we would especially like to hear about:

  • Anything that lets a user act above their role
  • Anything that lets one tenant read or write another tenant's workspace or credentials
  • Anything that escapes the workspace directory
  • Anything that makes the server send a request somewhere it should not
  • Anything that gets a stored credential back out to a browser
  • Anything that turns model content into executed code or unescaped HTML

You do not need a working exploit. A clear description of the flaw is enough. See the repository’s SECURITY.md for what is out of scope and what response times to expect.
