Getting started

Your first model, in five minutes

Sign in with GitHub, pick a repository, and start modelling. There is nothing to install and no server to run.

  1. Sign in

    Open Strata Cloud and choose Continue with GitHub. No separate account, no password to pick, no email to confirm.

  2. Pick a repository

    You are shown the repositories you can write to. Choose the one that holds your models, or an empty one if you are starting fresh. Strata fills it in.

    Whoever else has access to that repository can sign in and work in the same models. That is the whole of user management. See Strata Cloud for how permissions map across.

  3. Look around the example

    A new workspace opens on a small worked example: a shop, modelled across all three tiers. Small enough to hold in your head, complete enough to show the whole chain. The tour below walks through it.

Want to look around first?

Try it without an account. You get a private scratch workspace seeded with the example, nothing is saved, and no repository is touched. Useful for seeing what this is before you point it at anything of your own.

Need to run it yourself?

If your repositories live on an internal GitHub Enterprise Server, if your BigQuery project is only reachable from inside your network, or if a review says the working copy cannot leave your infrastructure, then self-host instead. Same software, and the tour below applies either way.

Take the tour

The example is deliberately small: two concepts become two entities become two BigQuery tables. Small enough to hold in your head, complete enough to show the whole chain.

  1. Look at the three tiers

    Open Models in the sidebar. You will see three:

    • shop_concept is what the business talks about. Customer. Order. No types, no keys, just ideas and how they relate.
    • shop_logical gives those ideas attributes, keys and logical types. Still nothing about BigQuery.
    • shop_warehouse is the real thing. STRING, NUMERIC, partitioning, clustering.

    These are not three views of one thing. They are three models, linked, so you can change the physical layer without touching the business definitions above it.

  2. Edit on the diagram

    Open shop_warehouse, then the Shop Mart diagram.

    • Double click a box title to rename the table.
    • Double click a row to change a column name or type.
    • Click Add column on a box to append one.
    • Right click a row to make it part of the primary key.

    Making a column part of the primary key also marks it as required, because a nullable key is not a key. Strata does that for you rather than reporting an error you then have to go and fix.

  3. Break something on purpose

    Rename customer_id on dim_customer to something else. Then open Problems.

    You will see the relationship to fct_order is now broken. Problems groups findings by rule, so one bad naming standard reads as "one rule, forty places" instead of forty separate things to read.

    Rename it back when you are done.

  4. See what it would generate

    On the model page, open the Output tab. This shows a changeset, not an inventory: the files that would change, not the ones that would not.

  5. Try the command palette

    Press Ctrl + K, or Cmd + K on a Mac. Type order.

    It searches commands, models and every object on the server, all the way down to column names. You do not need to know which model or folder something lives in to find it.

Working in your own models

You already chose the repository when you signed in, so there is nothing further to point anywhere. To work in a different one, open the workspace menu and pick another.

If the repository was empty, Strata offers to set it up on the first screen. That writes a strata.config.yaml and a .gitattributes. The .gitattributes matters more than it looks: it pins model files to LF line endings. Without it, git on Windows checks every file back out as CRLF, every file looks modified, and the diffs this tool exists to produce get buried.

Everything you change becomes a commit and a pull request in that repository. Nothing is stored anywhere you cannot see: git log in your own checkout shows exactly what Strata did.

Add the CI gate

This is the step that turns Strata from a drawing tool into a governance system, and it is the one people skip. It takes two minutes.

In your model repository, add this file:

.github/workflows/strata-check.yml

name: strata check

on: [pull_request]

jobs:
  check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
      - run: npx @strata/cli check --format github

Then turn on branch protection for main and require that check to pass.

--format github makes the findings appear as annotations on the changed lines of the pull request, rather than as a wall of text in a log nobody opens.

Why this matters

Strata can refuse to open a proposal when the model is invalid, but somebody can always push straight to main and go around it. Branch protection plus this check is what makes the rule real. Strata also generates a CODEOWNERS file from model ownership, so the right person has to approve.

If it does not work

Running your own instance? The environment and proxy problems are on the self-hosting page instead.

What you seeWhat is wrong
The first page takes about a minute Cloud sleeps after fifteen minutes of no traffic while it is free, and the first request wakes it. Later requests are immediate.
Your repository is not in the list Only repositories you can write to are offered, because a read-only one could never receive a change. Ask for write access, or pick another.
"This invitation is no longer valid" Invitation links work once and expire after seven days. Ask whoever sent it for a new one.
Every file looks modified in git and you did not touch them Line endings. Add the .gitattributes that strata init writes, then re-check out the files.
"Too many sign-in attempts" Working as intended. Wait the number of seconds it tells you. The delay resets after a successful sign in.
Something went wrong on the server Copy the request id from the message. Search your server logs for it and you will find the exact line, with the real error.
