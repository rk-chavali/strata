Self-hosting

Running Strata yourself

Everything runs in your infrastructure. Strata talks to exactly two things outside itself, both optional and both yours: your GitHub, so it can raise pull requests, and your own model provider, if you turn on agent skills. It never phones home.

Whether you need this

Most teams do not. Strata Cloud is the same software with nothing to install, and your models live in your own GitHub repository either way.

Self-hosting is the right choice when one of these is true:

  • Your repositories are on an internal GitHub Enterprise Server that a hosted instance cannot reach.
  • Your BigQuery project is only reachable from inside your network.
  • A review requires that the working copy never leaves your infrastructure.
  • You want local accounts rather than GitHub as the identity provider.

If none of those apply, start with Cloud and come back here if that changes. Moving either direction is just pointing a different instance at the same repository.

What you take on

Running it yourself means you are responsible for:

  • Provisioning and maintaining the server, and keeping the image up to date
  • TLS, and whatever sits in front of it
  • Backing up the data directory, which holds accounts and the session secret
  • Availability, and restoring it when something breaks

None of that is heavy. The container is stateless, the model is files in git, and the data directory is small enough to back up with tar. But it is real work, and it is worth knowing before you start rather than after.

The recommended way

Docker Compose. One file, one command, no build. It is what the walkthrough below uses and what most teams should pick. Kubernetes is covered too, for teams that already run one, and hosting options compares the platforms you might rent a machine from.

Where the packages are

Two published artefacts, both public. Neither needs a login, an account or a clone.

WhatPull it withEvery version
Container image docker pull ghcr.io/rk-chavali/strata:latest Package page
Helm chart helm pull oci://ghcr.io/rk-chavali/charts/strata Package page

The image is built for linux/amd64 and linux/arm64, so it runs on an Apple Silicon laptop and on the ARM instances that most free cloud tiers offer.

Which tag to use

latest is the newest release, and it is what the examples here use. Every tag that has ever been published is listed on the package page above, which is also where you can see when each was pushed.

Pin a version for production

latest moves across major versions, so a routine docker compose pull can bring a breaking change on a Tuesday morning. Naming a version instead means upgrades happen when you decide: 

image: ghcr.io/rk-chavali/strata:0.1.0

Helm takes the newest chart when no --version is given, and --version 0.1.0 pins it the same way.

What it stores, and where

This is the first question every security review asks, so it is the first thing here.

There is no database. The model is files in your git repository.

WhatWhere it livesIn your repo?
Models, all three tiersYAML filesYes
Diagrams, layout, shapesSeparate YAML filesYes
Settings, lint rules, conventionsstrata.config.yamlYes
Generated DDL and CODEOWNERSDDL/, CODEOWNERSYes
Accounts and password hashesSTRATA_DATA_DIRNo
Session signing secretSTRATA_DATA_DIRNo
Encrypted credentialsSTRATA_DATA_DIRNo
Delivery log and audit logSTRATA_DATA_DIRNo

So there are exactly two places with state, and both live outside the container image. /workspace is your model repository, a real git checkout. /data is everything that must never be committed to it.

Persist /data

If you lose it you lose accounts, stored credentials and the audit log, and everyone is signed out. You do not lose any models, because those are in git.

Walkthrough: Docker Compose

The most common way to run Strata for a small team. Start to finish, about fifteen minutes.

  1. Create the model repository

    If you do not have one yet, make an empty repository on GitHub and clone it onto the host. Strata will fill it in. 

    git clone git@github.com:your-org/data-models.git /srv/data-models

  2. Save the compose file

    Put this in an empty directory as docker-compose.yml. It is the whole install: there is nothing to clone and nothing to build, because it pulls a published image.

    docker-compose.yml

    services:
  strata:
    # `latest` is the newest release. Name a version instead for production,
    # so an upgrade happens when you decide. See "Where the packages are".
    image: ghcr.io/rk-chavali/strata:latest
    ports:
      - "4000:4000"
    environment:
      PORT: 4000
      STRATA_WORKSPACE: /workspace
      STRATA_DATA_DIR: /data
      STRATA_ADMIN_USERNAME: ${STRATA_ADMIN_USERNAME:-}
      STRATA_ADMIN_PASSWORD_HASH: ${STRATA_ADMIN_PASSWORD_HASH:-}
      STRATA_COOKIE_SECURE: ${STRATA_COOKIE_SECURE:-false}
      STRATA_TRUST_PROXY: ${STRATA_TRUST_PROXY:-false}
      GITHUB_TOKEN: ${GITHUB_TOKEN:-}
      GIT_AUTHOR_NAME: ${GIT_AUTHOR_NAME:-strata}
      GIT_AUTHOR_EMAIL: ${GIT_AUTHOR_EMAIL:-strata@localhost}
      GIT_COMMITTER_NAME: ${GIT_AUTHOR_NAME:-strata}
      GIT_COMMITTER_EMAIL: ${GIT_AUTHOR_EMAIL:-strata@localhost}
    volumes:
      # Your model repository, from the step above.
      - ${STRATA_WORKSPACE_HOST:?set this in .env}:/workspace
      # Accounts and the session secret. Not your models.
      - strata-data:/data
      # Only needed if your git remote uses SSH rather than HTTPS.
      - ${SSH_DIR:-~/.ssh}:/home/strata/.ssh:ro
    restart: unless-stopped
volumes:
  strata-data:

  3. Generate a password hash for the administrator

    Do this before the first start. It is what stops a stranger becoming your administrator if the data volume is ever lost. 

    docker run --rm -it ghcr.io/rk-chavali/strata \
  node apps/server/dist/hash-password.js

    It asks for a password without echoing it, then prints a hash that looks like scrypt$a1b2...$c3d4.... Copy that.

    The hash is safe to keep in a file or a secret manager. It cannot be replayed anywhere else, and it cannot be turned back into the password.

  4. Write your settings

    Create a .env file in the same directory:

    .env

    # Where your models live on this host
STRATA_WORKSPACE_HOST=/srv/data-models

# The administrator, created at boot if no account exists
STRATA_ADMIN_USERNAME=admin
STRATA_ADMIN_PASSWORD_HASH=scrypt$a1b2...$c3d4...

# Set both of these once you are behind HTTPS
STRATA_COOKIE_SECURE=true
STRATA_TRUST_PROXY=true

# Opens pull requests. Without it you still get branch, commit, push and a compare link
GITHUB_TOKEN=ghp_your_token_here
    Do not commit this file

    It holds a token and a password hash. Add .env to your .gitignore before you write it, not after.

  5. Start it

    docker compose up -d

    Then check the logs:

    docker compose logs -f

    You are looking for two lines:

    seeded the administrator from configuration
strata server listening on http://localhost:4000

    If instead you see a warning that /api/auth/setup is open, the seed did not take. Check the variable names and that the hash was copied whole.

  6. Sign in

    Open the address, sign in as the administrator you seeded, and change nothing yet. The Overview page carries a setup checklist that ticks itself off as git, a remote, a token and a first model appear. Work down it.

  7. Add your team

    Go to Settings, then Users. There are two ways, and they suit different situations.

    Send an invitation. Pick a role, create the invitation, and copy the link. Send it however your team already talks. The person opens it, chooses their own username and password, and lands in the workspace signed in.

    Or create the account directly. Faster if the person is sitting next to you, but you choose their password, which means you know it and it usually reaches them over chat in plain text. Prefer an invitation when it is not someone you can just tell.

    See People and roles for what each role can do.

    Want invitations to email themselves?

    Optional, and off until configured. Set smtp.host and smtp.from under Settings, Git and secrets, and an email field appears beside the invitation form. See configuration for the full list.

    No mail server needed

    Strata does not send email, and does not need to be configured to. The link is the invitation. It is single use, expires after seven days, and can be revoked from the same screen before it is used. The invitation code travels in the link's fragment, so it never reaches a web server log or a proxy along the way.

  8. Turn on the CI gate

    Add strata check to your model repository's pipeline and require it in branch protection. The quickstart has the workflow file.

    This is the step that makes the governance real, and the one most likely to be skipped. Strata can refuse to open a proposal, but nothing stops a direct push to main unless the repository requires review.

Seeding the administrator

Strata has no default password. Somebody has to create the first account, and until they do, /api/auth/setup is open to whoever gets there first.

On a laptop that is fine. On anything reachable from a network you do not control it is not, for a reason that is easy to miss: the route reopens whenever the data directory is empty. Forget the volume in docker run, or set persistence.enabled: false in the Helm chart, and every restart hands the next visitor an administrator account.

Set these two and there is no window at all, because the account exists before the server starts listening:

VariableWhat it is
STRATA_ADMIN_USERNAMEThe username to create.
STRATA_ADMIN_PASSWORD_HASHA hash from hash-password. Preferred, because it is safe to store anywhere.
STRATA_ADMIN_PASSWORDA plain password instead. Easier to try, worse to store.
Safe to leave in place

Seeding only happens when there are no accounts at all. Leaving these variables set after the first boot does nothing, so a password you later change in the UI is never quietly put back. If the hash is malformed, Strata refuses to start rather than booting without an admin.

Connecting GitHub

A token lets Strata open pull requests for you. Without one it still creates the branch, commits and pushes, then hands you a link to open the pull request yourself.

Three ways to supply it, best first:

  1. A mounted file. Set STRATA_GITHUB_TOKEN_FILE to a path. This is how Vault, Google Secret Manager and Kubernetes secrets all present themselves, so one mechanism covers all of them. The token never touches Strata's own disk, and it rotates without a restart.
  2. An environment variable. GITHUB_TOKEN. Fine for a small deployment. Be aware that environment variables show up in docker inspect and kubectl describe pod.
  3. Pasted into Settings. Stored encrypted in STRATA_DATA_DIR. Good for a team without a secret manager.

The token needs repo scope. Nothing more.

People and roles

RoleCan
viewerRead models, diagrams, the dictionary and lineage. Change nothing.
editorAll of the above, plus edit models and open pull requests.
adminAll of the above, plus settings, file layout, integrations, accounts and the audit log.

Roles are checked on the server for every request. The UI hides what your role cannot do, because a hidden button explains better than a refusal, but the server is what actually enforces it.

The last administrator cannot be demoted, disabled or deleted, so there is no way to lock yourself out.

Who can approve a change is a separate question

Worth separating two things that get confused. Who can use Strata is the role above. Who can approve a model change is not Strata's job, deliberately. That is CODEOWNERS plus branch protection in your own GitHub.

Strata generates the CODEOWNERS file from model ownership, and your existing review process enforces it. An editor in Strata can propose anything. What actually lands in main is governed by the same rules as the rest of your code.

What about single sign on

There is none yet. Two options today, and both have a real cost:

  • Local accounts. Works now. An admin creates each person. Fine for a team of five to twenty. Painful past that, and removing somebody is manual.
  • STRATA_AUTH=off behind an authenticating proxy. Your existing SSO does the authentication and Strata trusts the network. This is a real pattern, but Strata then has no idea who anyone is, so everybody is effectively an editor and commits are not attributed to individuals. That is a genuine loss, not just a preference.

Walkthrough: Kubernetes

The chart is published to the same registry as the image, so there is nothing to clone. On Kubernetes there is no host folder to mount, so the container clones your model repository on startup instead.

  1. Create the secrets

    kubectl create secret generic strata-github \
  --from-literal=token=ghp_your_token_here

kubectl create secret generic strata-admin \
  --from-literal=username=admin \
  --from-literal=passwordHash='scrypt$a1b2...$c3d4...'

  2. Write your values

    my-values.yaml

    model:
  repo: https://github.com/your-org/data-models.git
  branch: main

auth:
  enabled: true
  # Essential once you have an ingress. A Secure cookie over plain HTTP is
  # silently dropped by the browser, which looks like sign in not working.
  cookieSecure: true

github:
  existingSecret: strata-github
  existingSecretKey: token

# Holds accounts, the session secret, the encrypted token, the audit log,
# and the model checkout. Losing it signs everyone out.
persistence:
  enabled: true
  size: 5Gi

ingress:
  enabled: true
  className: nginx
  host: strata.your-company.com
  tls:
    enabled: true
    secretName: strata-tls

extraEnv:
  - name: STRATA_ADMIN_USERNAME
    valueFrom:
      secretKeyRef: { name: strata-admin, key: username }
  - name: STRATA_ADMIN_PASSWORD_HASH
    valueFrom:
      secretKeyRef: { name: strata-admin, key: passwordHash }
  - name: STRATA_TRUST_PROXY
    value: "true"

  3. Install

    helm install strata oci://ghcr.io/rk-chavali/charts/strata -f my-values.yaml

    Helm speaks OCI natively, so there is no repository to add first.

  4. Check it came up

    kubectl logs -l app.kubernetes.io/name=strata --tail=50

    Look for the clone succeeding and the administrator being seeded. If the clone fails, Strata still starts and shows the error in the UI, because a container that exits becomes a crash loop and a crash loop gives you nowhere to read the error.

Do not set persistence.enabled to false

It mounts an emptyDir, so /data is wiped on every restart. That signs everyone out, loses every stored credential and the whole audit log, and reopens first run setup unless you have seeded the administrator. It is there for a five minute smoke test and nothing else.

Behind a proxy

Two settings matter, and both cause confusing symptoms if you get them wrong.

Secure cookies

Set STRATA_COOKIE_SECURE=true whenever you serve over HTTPS. If you set it while still on plain HTTP, the browser drops the cookie without any error, and sign in appears to work while you stay signed out.

Trusting the forwarded address

Set STRATA_TRUST_PROXY=true when something sits in front of strata. This affects the sign in throttle. Leave it off behind a proxy and every visitor shares one counter, so one person guessing passwords locks out your whole company. Turn it on with no proxy in front and a client can claim any address it likes, which defeats the throttle entirely.

Do not buffer the event stream

The UI holds a long lived connection open for presence and live updates. A proxy that buffers responses holds those events until the buffer fills, which looks exactly like the feature silently not working.

For nginx:

proxy_buffering off;
proxy_read_timeout 3600;

The Helm chart already sets the matching ingress annotations.

Backups

Two things, and they need different treatment.

The models

Already backed up, because they are in git and pushed to your remote. Nothing to do. This is the main reason the whole tool is built this way.

The data directory

Back this up. It is small, usually well under a megabyte, and it holds the things that cannot be recreated: password hashes, the session signing secret, encrypted credentials and the audit log. 

# Docker Compose
docker compose exec strata tar czf - /data > strata-data-$(date +%F).tgz

# Kubernetes
kubectl exec deploy/strata -- tar czf - /data > strata-data-$(date +%F).tgz

A nightly copy is plenty. Losing a day of it costs you a day of audit log, and nothing else.

Or export a workspace

Any viewer can download the whole workspace as a .tgz from the UI, or directly: 

curl -b "strata_session=..." https://strata.your-company.com/api/workspace/export -o models.tgz

This is most useful for a workspace that is not a git repository yet, where there is no remote holding a copy.

Upgrading

  1. Read what changed

    Check the release notes for the version you are moving to.

  2. Back up the data directory

    See above. This is the one thing you cannot recreate.

  3. Pull and restart

    docker compose pull
docker compose up -d

    Or on Kubernetes:

    helm upgrade strata oci://ghcr.io/rk-chavali/charts/strata -f my-values.yaml

  4. Check it is healthy

    curl -s https://strata.your-company.com/api/health

    That returns {"ok":true} and nothing else, on purpose. For real numbers, sign in as an administrator and call /api/health/detail, which reports the build, the model count, git state and which features are enabled.

Model files are forward compatible. An older Strata reading a newer model file will report fields it does not understand rather than losing them.

Why only one replica

Strata runs as a single instance and there is no setting to change that. This is a correctness constraint, not a tuning choice.

The workspace is a git working tree on a volume. Two containers writing to one working tree corrupt it: one is halfway through a commit while the other is checking out a branch. There is no locking that fixes this, because git itself assumes one writer.

The Kubernetes deployment strategy is Recreate for the same reason. A rolling update would run two pods against that volume during every upgrade.

In practice this is rarely a limit. Strata reads YAML files and runs git commands. A team of fifty modelling all day does not trouble one small container.
